# 恢复提示为纯展示、不参与调度

需求原本规定"验证调度不读取或依赖上游响应中的恢复时间"。在 pools 视图新增列后，我们希望向用户展示上游在额度不足响应中主动给出的恢复时刻（例如 OpenCode Go 错误体里的 "Resets in 21min"），但仍然不希望这让路由器变成一个依赖上游承诺的调度器。

我们决定把"恢复提示"作为新的领域概念落地，明确其语义边界：上游提供、路由器只解析与展示、不参与调度。`NextVerifyAt` 继续由本地 `VerifyInterval` 推算，恢复提示过期仅导致显示空白，不触发任何状态或调度变化。同时放宽需求措辞，从"不读取"改为"不错开调度节奏"。

被拒绝的备选项：

- 展示并参与调度：若上游给出绝对时刻且晚于本地 `NextVerifyAt`，把探针推迟到该时刻。能避免在已知仍穷尽的凭证上空探针，但把验证节奏的权威从本地配置让渡给上游承诺，推翻验证间隔决策，并使凭证恢复行为依赖非结构化文本的解析正确性。
- 抓取但不持久化：仅当次显示，重启后空白。改动小，但跨会话无意义，用户会困惑。
- 将限额周期混入恢复提示配置：两者都从上游响应提取、配置形态相同，但语义不同——恢复提示是"何时好"，限额周期是"被哪个限额挡住"。混存会让配置字段名与含义脱节，并让未来分别演进（如限额周期纳入分类规则）受限。
